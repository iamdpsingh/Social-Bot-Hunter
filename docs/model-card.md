# Model card

## Summary

| | |
|---|---|
| Name | `account-risk` (rules), `coordinated-network` (graph) |
| Type | **Rules-based heuristic.** No machine-learning model exists in this version. |
| Versions | rules `rules-v1`, features `features-v1`, graph `similarity-louvain-1/rules-v1` |
| Output | Account: a 0-100 heuristic risk indicator or `insufficient_evidence`. Cluster: candidate group with signal strength and confidence. |

## Intended use

Helping a human analyst prioritise which accounts and groups to look at more closely, with the
evidence visible. It supports an investigation. It does not make decisions.

## Out-of-scope and prohibited use

* Treating a score or cluster as proof that an account is a bot or a group is coordinated.
* Reporting a "percentage of fake followers" from these scores.
* Automatic blocking, reporting, messaging, following, harassment, doxxing, or mass targeting.
* Linking accounts across platforms by username.
* Any use that bypasses privacy settings or platform access controls.

## Data

| | |
|---|---|
| Training data | **None.** Nothing is trained. |
| Tuning data | **None.** Weights and thresholds were chosen by hand for interpretability. |
| Labels | **None exist.** No labelled real-world accounts were used or are bundled. |
| Test fixtures | Fully synthetic, generated by `sbh.fixtures.synthetic`, labelled `synthetic` in every scan. |

## Evaluation

**No model-quality metrics are reported, because none have been measured.** Precision, recall, F1,
PR-AUC, false-positive rate, confusion matrices and calibration all require a labelled dataset with
documented provenance, and none has been built. Reporting them from synthetic data would be
misleading.

What does exist is a regression check: tests assert that the pipeline finds the structure planted in
the synthetic dataset (an obvious bot ring and two stealthier members), keeps a friend group at `low`
strength, and keeps organic synthetic accounts below the first risk band. That shows the code does
what the methodology says. It says nothing about accuracy on real accounts, and the synthetic data is
much cleaner than real data.

## Known limitations and failure modes

* **False positives** are expected for: new accounts, brand and organisational accounts, very active
  legitimate users, and tight friend groups or fandoms (which overlap structurally and are surfaced as
  `low`-strength clusters with alternative explanations).
* **False negatives** are expected for: bots with human-like profiles, content that is word-spun
  rather than templated, bots that avoid shared follow targets, and anything where the needed data
  was not collected (unavailable features lower coverage rather than raising suspicion).
* Heavy dependence on declared relationship-list coverage. Partial lists bias overlap measures.
* Thresholds are uncalibrated, so scores are ordinal indicators, not probabilities.
* Segment performance (by platform, account type, language, region) is unknown.

## Before any ML model is added

The specification requires, and this project will keep to: a documented dataset with provenance, a
label definition, an evaluation protocol that keeps coordinated clusters and related accounts on one
side of the train/test split, an intended-use statement, probability calibration against
representative labelled data if probabilities are ever displayed, and persisted model version,
training-data reference, feature schema and evaluation results (`model_versions` already has columns
for these). Predictions from one model are never used as labels for another.
